# Week 7: Advanced RAG & Knowledge

## Query Rewriting and HyDE {#query-rewriting-hyde}
<!-- emoji: ✏️ | minutes: 9 | related: similarity-search, rag-overview, agentic-rag -->

**TL;DR:** Query rewriting reshapes the user's raw question into better search queries, and HyDE searches with a model-written fake answer instead.

### Explain
Users type messy questions: "does it work with that thing from before?" Raw questions are often poor search queries. Advanced RAG improves the query *before* retrieval.

Techniques:
- **Rewrite / clarify** — a model turns chat context plus the question into a standalone query ("Does the Pro plan support SSO?").
- **Decomposition** — split a complex question into sub-questions, search each, combine.
- **Multi-query** — generate several paraphrases, search all, merge results (improves recall).
- **Step-back** — also search a more general version ("what is SSO setup?").
- **HyDE (Hypothetical Document Embeddings)** — ask the model to write a *plausible answer*, embed that, and search with it. A fake answer often sits closer in vector space to real answer passages than the short question does.

All of them add an extra model call, so you pay latency and cost to gain recall.

### Analogy
Asking a librarian a vague question, then having an assistant rephrase it into the exact catalogue terms before searching the shelves.

### Why it matters
In chat apps, follow-up questions like "and what about the price?" are meaningless without rewriting. If your RAG fails on follow-ups, query rewriting is the fix.

### Example
```
History: "Tell me about the Pro plan." → "How much is it?"
Rewrite → "What is the price of the Pro plan?"
HyDE → "The Pro plan costs $X per month, billed annually, and includes…"
        (embed this, then search)
```

### Takeaways
- Better queries retrieve better chunks.
- Rewrite, decompose, multi-query or HyDE depending on the failure.
- Each technique costs an extra model call.

### Glossary
- **Query decomposition** — breaking a complex question into simpler sub-queries.
- **Multi-query retrieval** — searching with several variants of the question.
- **HyDE** — retrieval using a model-generated hypothetical answer.

### Quiz
**Q:** A user asks "and how much is that?" after discussing a plan. What helps retrieval most?
- [ ] Increase the chunk size
- [x] Rewrite it into a standalone question using the chat history
- [ ] Lower the temperature
- [ ] Remove metadata
*Why:* Follow-ups lack context; rewriting makes the query self-contained and searchable.

**Q:** What does HyDE embed for the search?
- [ ] The user's account ID
- [ ] The entire corpus
- [x] A hypothetical answer generated by the model
- [ ] The system prompt
*Why:* A written-out answer resembles real answer passages more than a short question does.

## Metadata Filtering {#metadata-filtering}
<!-- emoji: 🏷️ | minutes: 8 | related: vector-database, privacy-pii, rag-failure-modes -->

**TL;DR:** Metadata filtering narrows a search by structured fields — date, author, product, permission — before or while doing similarity search.

### Explain
Similarity search knows meaning, not rules. It can't tell that a doc is from 2019, belongs to another customer, or is marked draft. Store **metadata** next to each chunk and filter on it.

Typical fields: `source`, `doc_type`, `date`, `version`, `language`, `product`, `team`, `tenant_id`, `access_level`.

Uses:
- **Freshness** — only docs from the last 12 months, or the latest version
- **Scope** — search only the "billing" docs when the user is in billing
- **Security** — only documents the current user is allowed to see (critical for multi-tenant apps)
- **Self-querying** — a model turns "2024 pricing from the EU team" into `{year: 2024, team: "EU"}` filters plus a semantic query

Filter *in the database query*, not after the model sees results — otherwise forbidden text has already leaked into the prompt.

### Analogy
A library catalogue where you can narrow by year, language and shelf before reading the blurbs.

### Why it matters
Permissions in RAG are a top security failure. "The chatbot revealed another customer's invoice" is usually a missing metadata filter.

### Example
```ts
index.search({
  vector: embed(query),
  topK: 8,
  filter: { tenant_id: user.tenantId, status: "published", year: { gte: 2024 } },
})
```
Without `tenant_id`, one customer's question could retrieve another's data.

### Takeaways
- Metadata adds exact, structured constraints to fuzzy semantic search.
- Use it for freshness, scoping and — critically — access control.
- Apply filters in the retrieval query, never after.

### Glossary
- **Pre-filtering** — applying filters before the vector search.
- **Multi-tenant** — one system serving many customers whose data must stay separate.
- **Self-querying retriever** — a model that extracts filters from natural language.

### Quiz
**Q:** Where must access-control filters be applied in RAG?
- [ ] After the model writes the answer
- [x] In the retrieval query, before text reaches the prompt
- [ ] In the CSS
- [ ] Only in the system prompt
*Why:* Once restricted text is in the prompt it can leak; the database must never return it.

**Q:** Why does pure vector search need metadata?
- [ ] Vectors don't exist without it
- [ ] To make embeddings shorter
- [x] It can't enforce exact rules like date, version or ownership
- [ ] To encrypt results
*Why:* Similarity is fuzzy; hard constraints need structured fields.

## GraphRAG and Knowledge Graphs {#graphrag}
<!-- emoji: 🕸️ | minutes: 10 | related: rag-overview, agentic-rag, vector-database -->

**TL;DR:** GraphRAG organises knowledge as entities and relationships, so the system can answer questions that require connecting many facts, not just finding one passage.

### Explain
Vector RAG retrieves similar passages. That struggles with questions like "What themes run across all our incident reports?" or "Who reports to the manager of the team that built Service X?" — the answer isn't in one chunk; it's in the **connections**.

A **knowledge graph** stores:
- **Nodes** — entities (people, products, companies, concepts)
- **Edges** — relationships (works_for, depends_on, acquired)

**GraphRAG** builds such a graph from your documents (often by having an LLM extract entities and relations), then retrieves by walking the graph: find the entity, follow edges, gather connected facts. Some versions also cluster the graph into communities and pre-write summaries for each, which helps with "big picture" questions.

Trade-offs: extra indexing cost, extraction errors, and more complexity. It shines on relationship-heavy data (org charts, legal, research, supply chains). For plain Q&A over docs, standard RAG is usually enough.

### Analogy
A detective's pinboard with strings between people and places, instead of a pile of separate witness statements.

### Why it matters
"Knowledge graph" and "GraphRAG" appear in architecture talks. You can now judge when the added complexity is justified: when relationships, not passages, hold the answers.

### Example
```
(Alice) -[manages]-> (Platform Team) -[owns]-> (Auth Service)
Q: "Who is accountable for Auth outages?"
Graph walk: Auth Service → owned by Platform Team → managed by Alice
```

### Takeaways
- Graphs capture relationships that chunk search misses.
- GraphRAG extracts entities and links, then retrieves by traversal.
- Worth it for connected, multi-hop questions; overkill for simple lookups.

### Glossary
- **Entity** — a distinct thing: person, organisation, product, concept.
- **Multi-hop question** — a question needing several linked facts.
- **Graph database** — storage optimised for nodes and edges, such as Neo4j.

### Quiz
**Q:** Which question most benefits from GraphRAG?
- [ ] "What's our refund window?"
- [x] "Which suppliers indirectly affect product X through other parts?"
- [ ] "Translate this sentence"
- [ ] "What's 2+2?"
*Why:* Indirect, multi-hop relationships are what graphs represent well.

**Q:** What is a drawback of GraphRAG?
- [ ] It can't use LLMs
- [ ] It forbids citations
- [x] Higher indexing cost and complexity, with possible extraction errors
- [ ] It only works offline
*Why:* Building and maintaining the graph is extra work and extraction can be wrong.

## Agentic RAG {#agentic-rag}
<!-- emoji: 🕵️ | minutes: 9 | related: what-is-agent, query-rewriting-hyde, rag-evaluation -->

**TL;DR:** In agentic RAG the model decides when, where and how often to search, rather than following a single fixed retrieve-then-answer pipeline.

### Explain
Classic RAG is a straight line: question → retrieve once → answer. It fails when the first search is wrong, or the question needs several lookups.

**Agentic RAG** turns retrieval into a *tool* the model can call in a loop:
1. Read the question and decide a plan
2. Call a search tool (maybe with a rewritten query)
3. Inspect results — are they sufficient and relevant?
4. If not: search again differently, try another source, or ask the user to clarify
5. Answer only when evidence is enough

It can route between sources (docs, SQL, web, code search), compare results, and verify its own claims.

Trade-offs: more flexible and robust, but slower, costlier, less predictable and harder to evaluate. Add step limits and logging. Use a simple pipeline for simple needs; go agentic when questions are varied and multi-step.

### Analogy
Instead of a vending machine (press button, get one item), a research assistant who searches, reads, realises it's the wrong report, and looks elsewhere.

### Why it matters
AI coding tools are agentic RAG over your repo: they grep, open files, re-search and then edit. Knowing the pattern helps you give better search hints ("check the auth folder first").

### Example
```
Q: "Why did revenue drop in March?"
1. search(sales_db, "March revenue")  → numbers
2. search(wiki, "March outage")       → incident report
3. synthesise → "Revenue dipped 8% due to the March 12 checkout outage [S2]."
```

### Takeaways
- Retrieval becomes a tool the model can call repeatedly.
- The model evaluates results and retries or switches sources.
- More capable but costlier and less predictable — add limits and logs.

### Glossary
- **Retrieval tool** — a function the model calls to search a data source.
- **Routing** — choosing which data source or index suits a question.
- **Self-reflection** — the model checking whether evidence is sufficient.

### Quiz
**Q:** What distinguishes agentic RAG from classic RAG?
- [x] The model can search multiple times and adapt its strategy
- [ ] It doesn't use a model
- [ ] It always uses a graph
- [ ] It stores answers in CSS
*Why:* Retrieval becomes an iterative tool-use loop instead of one fixed step.

**Q:** Which is a real downside of agentic RAG?
- [ ] It can never search the web
- [ ] It needs no prompts
- [x] More latency, cost and unpredictability
- [ ] It forbids tools
*Why:* Multiple model calls and decisions add time and variability.

## Document Parsing and OCR {#document-parsing-ocr}
<!-- emoji: 📄 | minutes: 9 | related: chunking, rag-failure-modes, foundation-multimodal -->

**TL;DR:** Before RAG can search your files, they must be turned into clean text; PDFs, scans, tables and images make that surprisingly hard.

### Explain
"Garbage in, garbage out" is most true here. A PDF isn't a text document — it's drawing instructions: put these glyphs at these coordinates. Extracting reading order is guesswork, especially with columns, headers, footers, footnotes and tables.

Layers of difficulty:
- **Digital PDFs** — text exists; extraction tools (PDF parsers) recover it, but layout can scramble.
- **Scans and photos** — pages are images. You need **OCR** (optical character recognition) to read characters.
- **Tables** — flattening them into lines destroys meaning; better to keep structure as Markdown, HTML or JSON.
- **Charts and diagrams** — text extraction misses them completely.

Modern approaches: layout-aware parsers, OCR models, and **multimodal / vision models** that look at the page image and describe or transcribe it. **Multimodal RAG** can embed images or page screenshots directly and retrieve them.

Always inspect parsed output with your own eyes before building on it.

### Analogy
Photocopying a magazine and reading it aloud in column order. Easy for a human; hard for a program that sees only ink positions.

### Why it matters
When your "chat with PDF" bot fumbles numbers in a table, the cause is almost never the LLM — it's parsing. Ask your assistant to preview extracted text first.

### Example
```
Raw extraction of a 2-column PDF:
"Revenue grew 12% Cost of goods Q1 Q2 Q3 5.1 5.3 …"   ← scrambled
Layout-aware output:
| Quarter | Revenue |
|---------|---------|
| Q1      | 5.1M    |
```

### Takeaways
- Parsing quality limits everything downstream.
- Scans need OCR; tables and charts need structure-aware or vision approaches.
- Always review parsed text before indexing.

### Glossary
- **OCR** — converting images of text into machine-readable characters.
- **Layout analysis** — detecting columns, headings, tables and reading order.
- **Multimodal model** — a model that understands more than text, such as images.

### Quiz
**Q:** A scanned contract returns empty text from a normal PDF parser. What's missing?
- [ ] A larger context window
- [x] OCR, since the pages are images
- [ ] A higher temperature
- [ ] A reranker
*Why:* Scans contain pixels, not text; OCR converts them into characters.

**Q:** Why do tables often cause wrong numbers in RAG?
- [ ] Models cannot read numbers
- [ ] Tables are encrypted
- [x] Flattening them loses row/column structure during parsing
- [ ] Embeddings reject digits
*Why:* If structure is destroyed at parse time, the model can't tell which value belongs where.

## RAG Evaluation {#rag-evaluation}
<!-- emoji: 📏 | minutes: 10 | related: evals-overview, reranking, grounding-citations -->

**TL;DR:** RAG evaluation measures retrieval and generation separately — did we fetch the right chunks, and did the answer stay faithful to them?

### Explain
"It seems to work" isn't evidence. A RAG system has two stages that fail independently, so you measure both.

**Retrieval metrics**
- **Context recall** — did the retrieved chunks contain the information needed?
- **Context precision** — how much of what was retrieved was actually relevant (vs noise)?
- **Hit rate / MRR** — is the right chunk in the top-k, and how high is it ranked?

**Generation metrics**
- **Faithfulness (groundedness)** — is every claim supported by the retrieved context?
- **Answer relevance** — does it actually answer the question asked?
- **Correctness** — does it match a known-good answer?

How: build a **golden set** of 30–100 real questions with expected answers/source docs, run the pipeline, score results, and re-run after every change. Scoring can use code checks, humans, or an LLM judge. Tools like Ragas or TruLens automate this.

### Analogy
Grading both a student's research (did they find the right books?) and their essay (did it follow the books?).

### Why it matters
Without evals, "improvements" like new chunk sizes are guesses. A small golden set turns RAG tuning from vibes into engineering.

### Example
```
Q: "What's the notice period?"   expected source: contract.pdf p.4
Retrieval: top-5 includes p.4? ✅ (recall)   3/5 chunks relevant (precision 0.6)
Answer: "30 days"  claims supported by p.4? ✅ (faithful)  matches truth? ✅
```

### Takeaways
- Evaluate retrieval and generation separately to locate failures.
- Faithfulness checks that answers stick to the retrieved context.
- A golden set makes every change measurable.

### Glossary
- **Golden set** — a curated list of questions with known-good answers or sources.
- **Context precision** — the fraction of retrieved chunks that are relevant.
- **MRR** — mean reciprocal rank, rewarding the right result appearing near the top.

### Quiz
**Q:** The right chunk was retrieved but the answer contradicts it. Which metric is low?
- [ ] Context recall
- [x] Faithfulness
- [ ] Chunk overlap
- [ ] Token count
*Why:* Faithfulness checks that the answer is supported by the retrieved context.

**Q:** Why separate retrieval and generation scores?
- [ ] To use more GPUs
- [ ] Because they're measured in different currencies
- [x] They fail independently, so you need to know which stage to fix
- [ ] The law requires it
*Why:* A bad answer could come from missing evidence or misusing it; each needs a different fix.

## RAG Failure Modes {#rag-failure-modes}
<!-- emoji: 🧯 | minutes: 10 | related: chunking, document-parsing-ocr, rag-evaluation -->

**TL;DR:** Most bad RAG answers trace back to a handful of predictable failures: bad chunks, missed retrieval, stale data, over-stuffing, or ignored context.

### Explain
When a RAG system disappoints, diagnose in pipeline order:

1. **Bad ingestion** — scrambled PDFs, lost tables, missing pages
2. **Bad chunks** — answers split across chunks, or chunks with no heading context
3. **Retrieval miss** — the right chunk exists but isn't in the top-k (synonyms, IDs, vague queries). Fixes: hybrid search, query rewriting, higher k + reranking
4. **Wrong-but-similar results** — close in meaning, but outdated, other product, or negated
5. **Stale data** — index not refreshed after documents changed
6. **Over-stuffing** — too many chunks dilute the prompt and trigger context rot
7. **Ignored or misread context** — the model answers from memory despite sources; fix with stronger grounding instructions
8. **Permission leaks** — filters missing, so users see data they shouldn't

Habit: log the question, retrieved chunks and answer for every request. You can't fix what you can't see.

### Analogy
A kitchen with a bad dish: was it the ingredients, the recipe, the chef or the plating? Check each step instead of blaming "the chef".

### Why it matters
When you tell your AI assistant "the bot is wrong", you can now be specific: "Check whether the right chunk is in the top 10." That one sentence saves hours.

### Example
```
Symptom: bot says refund window is 14 days (old policy)
Trace: retrieved chunk → policy_v1.pdf (stale)
Fix: delete old version / filter by latest version, re-index
```

### Takeaways
- Debug in order: ingestion, chunking, retrieval, ranking, generation.
- Stale data and over-stuffing are very common and easy to miss.
- Log retrieved context for every answer.

### Glossary
- **Index freshness** — how up to date the searchable data is relative to the source.
- **Top-k tuning** — adjusting how many chunks are retrieved.
- **Trace** — a recorded step-by-step history of a request through the pipeline.

### Quiz
**Q:** The bot quotes an outdated policy even though a new one was uploaded. Likely cause?
- [ ] The embeddings are too big
- [ ] The temperature is too low
- [x] The index still holds the old version or ranks it higher
- [ ] The model forgot English
*Why:* Stale or duplicate versions in the index are a classic RAG failure.

**Q:** What's a sensible first debugging step for a wrong answer?
- [x] Inspect which chunks were retrieved for that question
- [ ] Replace the model with a larger one
- [ ] Rewrite the system prompt in capitals
- [ ] Delete the vector database
*Why:* Seeing the retrieved chunks shows whether the failure is retrieval or generation.

## Semantic Caching {#semantic-caching}
<!-- emoji: 💾 | minutes: 8 | related: prompt-caching, similarity-search, caching-redis-cdn -->

**TL;DR:** Semantic caching reuses a previous answer when a new question means the same thing, saving cost and time without calling the model again.

### Explain
A normal cache needs an exact match: same key, same value. Users rarely repeat questions word for word — "How do I reset my password?" and "password reset steps?" are different strings with the same intent.

**Semantic caching** works like this:
1. Embed the incoming question
2. Search a cache of past question embeddings
3. If a stored question is similar enough (above a similarity threshold), return its saved answer
4. Otherwise call the model, then store the new question and answer

Benefits: big savings on repeated FAQ-style traffic, near-instant responses.

Risks:
- **Threshold too low** — returns a wrong answer for a *different* question ("cancel order" vs "cancel subscription")
- **Stale answers** — need expiry (TTL) and invalidation when facts change
- **Personalised content** — never cache answers that depend on the user's private data across users

Not the same as **prompt caching**, which reuses the provider's computation for an identical prompt prefix.

### Analogy
A receptionist who recognises "when do you open?" and "what are your hours?" as the same question and answers from a card instead of calling the manager.

### Why it matters
For public chatbots with many repeat questions, it can cut model bills sharply. Remember the two failure modes: wrong match and stale answer.

### Example
```
Cache: "How do I reset my password?" → "Go to Settings > Security…"
New:   "password reset steps?"   similarity 0.93 ≥ 0.90 → cache hit
New:   "How do I delete my account?" similarity 0.62 → cache miss → call model
```

### Takeaways
- Matches by meaning of the question, not exact text.
- The similarity threshold balances savings against wrong answers.
- Use TTLs and never share user-specific answers between users.

### Glossary
- **Similarity threshold** — the minimum score at which two questions count as the same.
- **TTL** — time to live; how long a cached item remains valid.
- **Cache invalidation** — removing or updating cached data when it becomes outdated.

### Quiz
**Q:** What risk does a too-low similarity threshold create?
- [ ] The cache becomes encrypted
- [x] It may return an answer for a different question
- [ ] The model stops working
- [ ] Embeddings become longer
*Why:* Loose matching treats distinct questions as the same and serves the wrong cached answer.

**Q:** How does semantic caching differ from prompt caching?
- [ ] They are identical
- [ ] Semantic caching only works on images
- [x] Semantic caching returns a stored answer for similar questions; prompt caching reuses processing of an identical prompt prefix
- [ ] Prompt caching needs a vector database
*Why:* One skips the model call entirely for a similar question; the other still calls the model but cheaper.
